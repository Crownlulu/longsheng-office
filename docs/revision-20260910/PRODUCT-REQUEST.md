# 办公协同产品 Demo 修改方案

> 依据：2026 年 9 月 10 日《办公协同产品 demo 优化讨论》智能纪要与逐字稿，并结合当前线上 Demo 和 `codex/office-assistant-handoff` 分支现状整理。  
> 用途：供技术同事及其 Codex 直接据此修改 Demo。  
> 口径：正文优先记录会议中已经明确的修改方向；会议中存在冲突、未给出具体内容或需要产品补充的部分，集中放在“待产品确认”，避免技术自行猜测。

## 一、本轮改版目标与范围

本轮首先把现有“供应商交期变更”单条核心链路的页面结构和交互做通，使销售可以拿 Demo 面向客户顺畅演示。重点不是继续堆功能，而是解决以下问题：

- 办公协同首页过于简单、单薄，不像企业级办公协同产品。
- 业务助手既不像 Chatbot，也不像任务办理页面；进入后信息一次性全部平铺，页面过长。
- 内部设计链路和内部步骤被直接展示给客户，不符合外部演示口径。
- 方案选择、任务发送、任务接收和回执等关键节点缺乏真实可点击的交互。
- 事项详情信息分散、字号小、层级不清，无法一目了然地回顾事项。
- 「演示设置」对客户演示没有价值，应从产品界面删除。

本轮最终保留三个核心入口：

1. 办公协同
2. 业务助手
3. 事项详情

## 二、办公协同 / 首页

### 1. 重做企业级首页布局

- 当前首页只有一条事项和一条待办，视觉与内容都过于单薄，需要重新设计。
- 首页应体现“办公协同总览”，而不是只展示一张供应商延期卡片。
- 建议至少形成以下信息层级：
  - 顶部：事项状态概览，例如预警、处理中、已办结数量。
  - 中部：需要用户关注的事项列表或事项卡片。
  - 下部或独立区域：我的待办，展示当前岗位真正需要处理的工作。
- 页面应通过分组、卡片、列表和状态标签建立清晰层级，避免把所有业务内容无序堆在同一页面。
- 视觉标准按面向大型企业客户演示的办公产品处理：信息密度适中、结构清楚、状态明确、页面不能显得空或粗糙。

**验收口径**：用户进入首页后，能快速看出当前有多少预警、多少处理中事项、多少已办结事项，以及本人下一步需要处理什么；页面不再只有一张孤立的大卡片。

### 2. 建立统一的事项状态分类

- 首页事项至少按以下状态组织：
  - 预警 / 警报：新发生、尚未进入处理或需要关注的异常事项。
  - 处理中：已进入方案分析、确认或部门执行阶段的事项。
  - 已办结：已经完成回执和最终复核的事项。
- 同一事项在处理链路推进后，应自动进入对应状态，不得在多个分组中重复出现或状态不一致。
- 当前“供应商交期变更”在完成最终人工复核并关闭后，应从预警或处理中转入已办结。
- 已办结仅代表办公协同事项闭环，不代表实物已经到货、生产完成或订单已经交付；界面文案需继续保留这一业务边界。

**验收口径**：从新预警到处理中再到已办结，事项状态变化可在首页清楚验证；关闭后不会从系统中消失，也不会继续出现在待处理区域。

### 3. 丰富“我的待办”

- 当前“我的待办”只有一项，内容过于单薄，需要补充演示数据和状态展示。
- 待办应随当前岗位变化，只显示该岗位可以或需要执行的动作。
- 每条待办建议展示：事项名称、当前阶段、来源或关联对象、责任岗位、截止或风险提示、当前状态和进入办理入口。
- 不同状态的待办需要有统一展示规则，例如待确认、待发送、待接收、处理中、待回执、待复核、已完成。
- 不要为了填满页面而重复展示同一条业务信息；补充的数据应能支持真实筛选、跳转和状态变化。

**验收口径**：切换业务负责人、采购、质量和销售岗位时，“我的待办”会显示与该岗位匹配的事项和操作；无待办时有清晰空状态。

### 4. 首页与后续页面的跳转

- 点击事项卡片进入该事项的详情页。
- 点击“继续处理”进入业务助手，并携带当前事项上下文。
- 首页进入业务助手时可以预填与该事项相关的问题或办理提示，但不得自动发送问题，也不得自动执行任何业务动作。
- 返回首页后保留事项当前处理状态，不应重置或丢失之前的对话、方案选择和任务进度。

### 5. 新增业务场景的阶段处理

- 会议明确认为目前只有“供应商交期变更”一个场景过于单一，后续需要增加适合公司业务的其他办公协同场景。
- 但会议最后同时确认当前阶段先把一条核心链路做顺。因此建议分两阶段实施：
  - 第一阶段：完成本文件中现有供应商延期链路的页面和交互改版。
  - 第二阶段：再新增至少 2 个公司业务场景，并复用同一套预警、处理中、已办结和待办展示逻辑。
- 会议没有确定新增场景的具体业务内容，技术本轮不要自行虚构正式场景和规则。

## 三、业务助手

### 1. 页面改为标准 Chatbot 结构

- 业务助手主界面应以 Chatbot / 对话框为核心，不再采用当前“对话入口 + 全部业务模块长页面平铺”的混合形式。
- 建议页面结构：
  - 左侧窄栏：历史会话列表，可新建、切换或返回历史会话。
  - 中间主区：当前事项的对话消息流、推荐问题和逐步出现的业务结果。
  - 底部固定输入区：问题输入框、发送按钮和必要的停止 / 重试状态。
- 历史问答不得继续放在页面最底部。
- 当前事项名称和必要状态可以放在对话区顶部，但不要用大段固定模块挤压对话空间。

**验收口径**：进入业务助手后，第一视觉中心是对话区；历史会话位于侧边；输入框始终易于找到；页面不再以超长静态报告的形式出现。

### 2. 初始状态不得平铺全部内容

- 用户刚进入业务助手时，只展示：
  - 当前事项的简短上下文。
  - 推荐问题，例如查询到料影响、核对会议决定、查询切换条件、查询处理进度。
  - 问题输入框。
- 用户点击推荐问题或发送自定义问题后，再显示本次查询对应的回答和结果模块。
- 会议决定、订单影响、方案比较、质量核验、任务和最终复核不得在首次进入页面时全部展开。
- 查询结果按用户当前问题逐步呈现；未触发的后续办理模块保持隐藏或显示简洁的下一步入口。

**验收口径**：首次进入页面时看不到完整 A/B 比较、任务回执和最终复核；发送“哪些订单受影响”后只出现与影响相关的回答、数据和来源入口。

### 3. 删除对外展示的内部八步链路

- 删除页面顶部当前展示的八步流程清单：延期通知、影响分析、会议决定、方案比较与选择、质量核验、负责人确认、部门执行、回执与关闭。
- 这八步属于内部方案和流程设计，不应直接展示给外部客户。
- 删除的是“把八个内部步骤列在页面上”的表现形式，不是删除背后的业务流程和状态守卫。
- 用户应通过自然对话、逐步出现的操作卡片和状态变化感受到流程，而不是看到内部流程图或实施清单。

**验收口径**：业务助手页面不再出现完整八步编号清单，但实际方案选择、核验、批准、任务和回执链路仍然可以按顺序完成。

### 4. 删除右侧冗余提示栏

- 删除当前右侧的以下固定模块：
  - 下一步处理
  - 质量条件
  - 负责人确认
  - 当前事项固定摘要
  - 其他与详情页重复的提示卡片
- 这些内容如确实与当前对话有关，应在对应回答、操作卡片或事项详情中按需展示，不要长期占据业务助手右侧。
- 删除后优先扩大主对话区，避免正文区域过窄。

### 5. 查询结果与来源交互

- 保留当前已有的订单影响、会议决定追溯和来源查看能力，但改为查询后按需出现。
- 查询结果不能只是一段模型文字；涉及订单、决定或方案时，应配套简洁的结构化卡片或表格。
- 会议纪要、订单台账等来源入口必须可点击，点击后可查看对应原文或证据内容。
- 来源查看后应能返回当前对话，并保留用户已发送的问题、结果和未完成的操作。
- 旧回答继续保留原始内容和当时的数据版本标识，避免历史回答随着当前状态被静默改写。

**验收口径**：用户发送问题后能看到回答和来源；来源按钮可点击；关闭来源后回到原对话位置；刷新或切换页面后，已完成的历史问答仍可恢复。

### 6. 方案比较与选择

- A/B 方案比较必须可点击、可选择，不能再出现“看得到但点不动”的情况。
- 每个方案清晰展示已有依据支持的优点、缺点、风险和前置条件。
- 不得补写资料中不存在的价格、产能、运输条件或综合评分。
- 用户选择某个方案时，系统自动带出该方案的主要选择依据；“本次选择或改选的原因”改为可选，不再强制手工填写。
- 方案选择只记录选择意向，不等同于负责人最终批准。界面必须清楚区分“已选择”和“已批准”。
- 未选择方案之前，不展示采购 / 销售任务回执和最终复核模块。

**验收口径**：用户可以直接点击选择 A 或 B；不填写补充理由也可以继续；选择后出现与该方案相匹配的下一步操作，但不会自动完成批准或任务下发。

### 7. 增加“方案都不满意”机制

- 在 A/B 方案选择区域增加“都不满意 / 重新生成方案”按钮。
- 点击后弹出输入窗口，让用户填写希望修改的方向、约束条件或不满意原因。
- 用户确认后，基于该反馈重新生成或调整方案；原方案与用户反馈需要保留在当前会话中，便于追溯。
- 重新生成方案不得自动写入业务状态，用户仍需重新选择并按原流程确认。
- 如果真实模型调用失败，应明确显示失败并允许重试，不得静默替换成规则答案。

**验收口径**：点击“都不满意”可输入修改意见并获得新方案；取消弹窗不改变现有选择和事项状态。

### 8. 质量核验

- 按本次会议口径，质量核验的对象是“方案质量”，页面文案、操作名称和说明需要统一，避免用户误解为泛化的产品质量、供应商质量或其他核验。
- 只有选择了需要核验的方案后，才展示质量核验相关操作。
- 核验发起、核验结果和凭据应显示在当前方案上下文中，不要提前展示空模块。
- 核验仍需保留责任岗位和人工确认，不能由助手自动判定并直接通过。

**验收口径**：未选择方案时不出现可执行的核验模块；进入核验阶段后，用户能明确看到核验对象、责任人、结论和凭据。

### 9. 负责人确认与任务下发

- 方案完成必要核验后，由业务负责人进行明确确认。
- 负责人确认后，才允许向采购和销售下发任务。
- 任务下发增加清晰的人工确认动作，例如“确认并发送任务”，不得在方案选择后自动静默发送。
- 采购和销售两条任务分别展示完整状态，至少应覆盖：
  - 待发送
  - 已发送
  - 已接收 / 已确认收到
  - 处理中
  - 已提交回执
  - 发送失败 / 可重试
- 页面需要显示采购和销售是否收到任务以及各自的反馈，不能只显示“尚未发起任务”。
- 发送失败和业务处理失败必须分开表达；重试沿用原任务，避免生成重复任务。

**验收口径**：负责人确认前无法发送采购、销售任务；点击发送后能分别看到两方的送达和接收状态；一方失败不影响另一方状态显示，并可人工重试失败任务。

### 10. 回执与最终复核

- 只有任务下发并进入执行阶段后，才展示采购和销售的回执区域。
- 采购、销售可以按任意顺序提交回执；每份回执显示提交人、提交时间、处理说明和凭据。
- 一份回执完成时显示“等待另一方回执”，不得提前出现可关闭事项的状态。
- 两份回执齐全后，向业务负责人展示最终复核入口。
- 最终复核需要负责人主动确认；关闭后更新事项状态并返回办公协同首页的已办结分类。
- 关闭时继续提示：关闭办公协同事项不代表原料已到货、生产已完成或订单已交付。

**验收口径**：未选方案时看不到回执模块；任务未发送时不能提交回执；回执未齐不能关闭；两份回执齐全并由负责人确认后，事项进入已办结。

## 四、事项详情

### 1. 增加“事项列表”和“单条详情”两种状态

- 从左侧导航直接进入「事项详情」时，首先展示事项列表，而不是直接固定展示供应商延期这一条事项。
- 事项列表顶部增加关键筛选框，至少支持按事项状态和关键词筛选；后续场景确定后再补充业务类型、责任岗位或时间等筛选条件。
- 列表应能承载系统使用后积累的大量历史事项，而不是只为单条 Demo 数据设计。
- 从业务助手点击“查看事项详情”时，直接进入当前事项的单条详情，不需要先经过列表。
- 单条详情左上角增加“返回事项列表”入口。

**验收口径**：从导航进入看到可筛选的事项列表；从业务助手进入直接看到对应事项详情；点击左上角可返回列表，并保留原筛选状态。

### 2. 重构单条事项详情的信息层级

- 当前详情页内容卡片过多、结构松散、字号偏小，需要合并和重新分组。
- 详情页应回答四个核心问题：
  1. 发生了什么。
  2. 影响了什么。
  3. 采用了什么方案、依据是什么。
  4. 当前处理到哪一步、结果是什么。
- 建议按以下结构整合：
  - 事项摘要：标题、编号、状态、关键对象、发生时间或演示日期。
  - 当前情况与影响：延期变化、关联订单、风险结论。
  - 方案与决定：比较结果、用户选择、负责人批准、当前有效决定。
  - 执行与回执：采购、销售任务状态、回执和最终复核结果。
  - 来源与处理记录：会议原文、台账、操作时间线。
- 相同信息不要在多个卡片中重复出现；次要内容使用折叠区，不要让页面首屏承载全部明细。
- 提升正文和关键数字字号，强化标题、状态、风险和结论的视觉层级。

**验收口径**：不展开高级内容时，用户在一页内即可理解事项起因、影响、方案、决定和当前进度；页面不再出现大量重复的小字卡片。

### 3. 保留高级视图

- 保留当前详情页底部高级视图中的以下能力：
  - 业务关系
  - 业务对象
  - 模型结构
- 高级视图默认折叠，仅供需要深入查看的用户展开。
- 会议只要求保留这些模块，并未要求本轮重做其数据模型；除修复明显显示问题外，不扩大范围。

### 4. 调整“返回助手继续办理”按钮

- 将“返回助手继续办理”从当前页面上方或右侧卡片移到单条事项详情的最底部。
- 使用醒目的大按钮，文案保持明确，例如“返回业务助手继续办理”。
- 点击后回到当前事项对应的助手会话，并保留问题、回答、方案选择草稿和处理进度。

**验收口径**：用户浏览完详情后在页面底部可清楚找到返回入口；返回后仍是同一事项和同一会话，不会新建空会话或丢失上下文。

## 五、演示设置与导航

### 1. 删除「演示设置」页面

- 从左侧导航删除「演示设置」入口。
- 从面向客户的页面结构中删除整个「演示设置」页面，不再展示：
  - 模型地址和模型名称配置。
  - API 密钥输入。
  - 规则模式 / 真实模型模式切换。
  - 调整到料日。
  - 模拟发送失败。
  - 同题对比和运行记录。
  - 重置演示空间。
- 本次会议决定的是删除客户可见页面。若研发、测试或部署仍依赖这些能力，可保留后端接口或改为非导航的内部调试入口，但不能继续暴露在销售演示主流程中。

**验收口径**：客户可见导航只剩办公协同、业务助手、事项详情；通过正常界面无法进入演示设置页。

### 2. 统一页面跳转和上下文

- 三个核心页面围绕同一个当前事项工作，跳转时必须保留事项 ID、当前岗位、对话历史和业务状态。
- 浏览器返回 / 前进、页面刷新以及岗位切换后，不得跳到错误事项或恢复成过期的可执行操作。
- 列表筛选状态、对话草稿和未完成操作应在合理范围内保留。

## 六、必须删除或避免的展示

- 不向客户展示内部八步流程清单或内部实施方案。
- 不在业务助手右侧保留“下一步处理、质量条件、负责人确认”等固定提示卡片。
- 不在用户尚未选择方案时提前展示任务回执和最终复核。
- 不强制用户手工填写方案选择原因。
- 不让“选择方案”在视觉或状态上等同于“负责人批准”。
- 不让不可点击的卡片或按钮看起来像可以交互。
- 不把所有查询结果、来源、方案、任务和回执一次性平铺在首屏。
- 不在事项详情中重复堆叠同一结论或使用大量难以阅读的小字。
- 不在客户演示导航中保留「演示设置」。

## 七、技术实现对应位置

以下是当前分支中与本次修改直接相关的主要文件，供技术同事和 Codex 定位；最终可根据重构结果拆分组件：

- `src/features/office/index.tsx`：页面状态、导航、访问入口、岗位切换、页面装配。

- `src/features/office/business.tsx`：当前办公协同首页和事项详情，需要拆分首页、事项列表、单条详情的结构。

## 八、待产品确认

## 九、建议实施顺序

1. 先调整导航和页面路由：保留三页，删除客户可见的演示设置，增加事项列表 / 单条详情状态。
2. 重构业务助手首屏和历史会话侧栏，删除八步清单及右侧冗余模块。
3. 将查询结果改为发送问题后渐进展示，并修复来源、会议纪要和方案卡片的点击交互。
4. 完成方案选择、可选理由和“都不满意”反馈重生成流程。
5. 补全方案核验、负责人确认、任务发送 / 接收、双回执和最终复核的渐进式交互。
6. 重构事项详情，将重复信息合并，保留折叠的业务关系、业务对象和模型结构。
7. 重做办公协同首页的状态概览、事项分组和我的待办，并打通关闭后转入已办结的逻辑。
8. 最后补做响应式、刷新 / 前进后退、岗位切换、失败重试和历史恢复测试。
9. 第一阶段验收通过后，再由产品补充至少 2 个新场景，复用统一列表与状态框架。
